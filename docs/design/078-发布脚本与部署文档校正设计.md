## 1. 背景与目标

- 现状与问题：
  - `docs/deployment-todo.md`、`deploy/nginx/`、`deploy/systemd/`、`.dockerignore`、两个运维脚本等部署产物长期只在本地与服务器上，未入库，换机即丢。
  - 系统提醒单元（unit）的 `Description` 仍写 `100.100.0.0/16`，实际规则已是 `100.64.0.0/10`；`ExecStart` 指向 `/usr/local/bin/*.sh`，与仓库里的 `scripts/*.sh` 文件名不一致，靠人工改名安装。
  - 两个脚本在仓库里没有执行位，`rsync -a` 同步后直接 `Permission denied`。
  - 提交会由 pre-commit 钩子把 `VERSION` 自增（当前 1.0.6 → 1.0.7），但服务器 `/srv/quizgo/.env` 的 `APP_VERSION` 不会自动同步，导致 `/v1/meta` 长期报旧版本。
  - `docs/deployment.md` 仍把 Prometheus 当作标准组件、备份章节仍是 custom format + WAL 的旧稿，`/healthz` 与 `/readyz` 的口径也不统一。
- 本次目标（可验证）：
  1. 仓库内的 unit 与脚本可直接安装运行，文件名、路径、描述三处一致。
  2. 一条命令完成「备份 → 打回滚点 → 同步 → 版本对齐 → 构建 → 迁移+重启 → 自检」，且 `/v1/meta` 与 `VERSION` 必然一致。
  3. `docs/deployment.md` 与线上实际形态一致，不再误导排查。
- 非目标（明确不做什么）：
  - 不改 nginx 监听端口（备案前保持 8081/8082），不动安全组、不动 `ts-input` 例外规则。
  - 不引入 CI/ACR 镜像仓库（P3 事项）。
  - 不改 `docs/deployment-todo.md`（由 Atlas 侧统一维护，见风险 R3）。
  - 不动业务代码与数据库迁移。

## 2. 需求与验收标准

| 编号 | 需求 | 验收标准 | 优先级 |
| --- | --- | --- | --- |
| R1 | unit 描述与实际规则一致 | `systemctl cat` 中不出现 `100.100.0.0/16`，统一为 `100.64.0.0/10` | P0 |
| R2 | 脚本在仓库中可执行 | `git ls-files -s scripts/backup-pg.sh` 显示 `100755` | P0 |
| R3 | unit 直接指向仓库脚本 | `ExecStart=/srv/quizgo/scripts/backup-pg.sh`、`/srv/quizgo/scripts/tailscale-aliyun-fix.sh`，服务器上无需再改名到 `/usr/local/bin` | P0 |
| R4 | 一键发布脚本 | `scripts/deploy.sh` 依次完成备份、回滚打标、rsync、`.env` 版本对齐、构建、`up -d`（含 migrate）、自检；失败时非 0 退出 | P1 |
| R5 | 版本真空期闭环 | 提交升版后执行 `scripts/deploy.sh`，`/v1/meta` 版本等于 `VERSION` | P1 |
| R6 | 文档与线上一致 | `docs/deployment.md` 中 Prometheus 标为未启用、备份章节为 gzip 纯 SQL + timer、探针分工明确 | P1 |
| R8 | nginx / systemd 配置随发布同步 | 改 `deploy/nginx` 必须加 `--with-nginx`（先 `nginx -t` 再 reload）；改 `deploy/systemd` 必须加 `--with-units`；漏加参数直接拒绝 | P1 |
| R9 | 发布基线可信 | 基线解析不到、或上次是脏工作区发布时，拒绝 `--skip-build` / `--skip-backup` | P1 |
| R7 | Prometheus 目录不误导 | `deploy/prometheus/README.md` 说明「预留，当前未启用」 | P1 |

## 3. 方案对比与选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 维持 `/usr/local/bin` 安装名，仓库内改名对齐 | 不动服务器 unit | 仓库与线上两套文件名，仍需人工改名；脚本改完要手动再复制一次 | 否 |
| B. unit 直接指向 `/srv/quizgo/scripts/*.sh` | 一处真源，`rsync` 同步即生效；不再有「改了仓库忘了复制」 | unit 依赖部署目录位置（本来就是固定约定） | **选用** |
| C. 把脚本做成镜像内命令 | 与容器一致 | 备份/网络修复是宿主级操作，不该进容器 | 否 |

发布脚本的方案对比：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 只 `up -d --force-recreate api worker` | 快 | **不会跑新迁移**，且跳过备份，直接踩红线 6 | 否 |
| B. `docker compose up -d` + 前置备份与回滚打标 | 由 compose 依赖关系保证 migrate 先跑；镜像变更会重建 migrate | 比 A 慢几十秒 | **选用** |

## 4. 总体架构

- 模块划分与职责：
  - `scripts/deploy.sh`：发布编排（宿主侧），不含业务逻辑。
  - `scripts/backup-pg.sh`：数据库备份（systemd 调用，也可手工调用）。
  - `scripts/tailscale-aliyun-fix.sh`：`ts-input` 例外规则自愈（systemd timer 调用）。
  - `deploy/systemd/*`：以上两个脚本的调度单元。
- 关键流程：

```
deploy.sh
  ├─ ssh: docker tag openquizgo:local openquizgo:rollback
  ├─ ssh: systemctl start quizgo-backup.service      （迁移不可逆，先备份）
  ├─ rsync: 本地 → /srv/quizgo（排除 .git/.env/node_modules/admin-web/dist）
  ├─ ssh: sed APP_VERSION=<VERSION> /srv/quizgo/.env
  ├─ ssh: systemctl-daemon-reload（可选，--with-units 时）
  ├─ ssh: docker compose build api && docker compose up -d
  │        └─ migrate（一次性，成功后才起 api/worker）
  └─ 自检：compose ps / /v1/meta 版本 / 日志无 error
```

- 目录结构影响：新增 `scripts/deploy.sh`、`deploy/prometheus/README.md`，其余为就地修正。

## 6. 接口设计

`scripts/deploy.sh` 的调用契约（非 HTTP）：

| 类型 | 名称 | 入参 | 出参 | 说明 |
| --- | --- | --- | --- | --- |
| CLI | `scripts/deploy.sh` | `--with-admin-web` / `--with-units` / `--skip-backup` / `--dry-run` | 退出码 0/1 | 环境变量 `SSH_HOST`（默认 `quizgo`）、`REMOTE_DIR`（默认 `/srv/quizgo`）、`BASE_URL`（默认 `http://quizgo-ecs:8082`） |

错误处理：任一步失败立即 `set -e` 退出；自检阶段对 `/v1/meta` 重试最多 60 秒，超时视为失败并提示回滚命令。

## 7. 非功能要求

- 性能：发布耗时由镜像构建决定（2C2G 约 1–3 分钟）；脚本本身无额外开销。
- 安全与权限：不传输 `.env`；备份产物含 `.env` 快照，仅留在 `/srv/backup/pg`（600），异地备份只上传 `*.sql.gz`。
- 可观测性：脚本每一步打印命令与阶段名，便于归档复盘。
- 兼容性与可维护性：macOS 自带 `openrsync` 支持所用参数；`docker compose` ≥ 2.26。

## 8. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| R1 unit 改路径后路径不可执行 | 备份/自愈失效且无人察觉 | 中 | 改完立即 `systemctl start` 两个 unit 验证退出码；`systemctl is-enabled` 复核 |
| R2 发布时漏跑迁移 | 新代码面对旧表结构报错 | 中 | 用 `docker compose up -d`（依赖 `service_completed_successfully`）而非只重建 api/worker |
| R3 与 Atlas 侧同时改 `docs/deployment-todo.md` | 两边互相覆盖 | 中 | 本次不改该文件，需要改动走 Atlas 侧 |
| R4 提交即升版，服务器滞后 | `/v1/meta` 报旧版本，排查被误导 | 高 | 提交后立刻执行 `scripts/deploy.sh`，并在 `AGENTS.md` 第八节写明强制要求 |
| R5 2C2G 构建期间并行操作 | OOM | 低 | 构建窗口内不跑备份/压测 |
