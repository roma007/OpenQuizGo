## 1. 背景与目标

- 现状与问题：
  - 管理后台只有登录/登出，没有改密入口；后端也没有改密接口，只能通过 `docker compose run … /app/admin passwd` 操作。
  - 2026-11-23 因管理员口令在会话中泄露，两次只能用 CLI 轮换，说明缺口已经造成实际成本。
  - 令牌是 JWT，有效期 8 小时，服务端无吊销机制：改密后旧令牌在过期前仍然有效。
- 本次目标（可验证）：
  1. 登录后在后台任意页面可自助改密，不需要 CLI。
  2. 改密必须校验当前口令；新口令满足长度与基本强度要求。
  3. 改密成功后，当前会话与其它已登录会话**全部失效**，强制重新登录。
  4. 改密失败有明确的错误码与次数限制，不泄露「旧口令是否正确」以外的信息。
- 非目标：
  - 不做找回密码 / 邮件重置 / 双因素认证。
  - 不做管理员列表、角色管理（现有 RBAC 不动）。
  - 不改登录接口契约与 Cookie 策略。

## 2. 需求与验收标准

| 编号 | 需求 | 验收标准 | 优先级 |
| --- | --- | --- | --- |
| R1 | 改密接口 | `POST /v1/admin/auth/password`，需登录，返回 200 并清除 Cookie | P0 |
| R2 | 当前口令校验 | 旧口令错误返回 `401 AUTH_INVALID_CREDENTIALS`，不更新哈希 | P0 |
| R3 | 新口令规则 | 12–72 字节（字符下限 12）：不得与旧口令、用户名相同；不满足返回 `422 VALIDATION_ERROR` | P0 |
| R4 | 会话失效 | 改密后旧令牌（含其它浏览器）全部 401，需重新登录 | P0 |
| R5 | 暴力尝试限制 | 同一账号 15 分钟内错误 5 次返回 `429 RATE_LIMITED` | P0 |
| R6 | 前端入口 | 顶栏用户区出现「修改密码」，弹窗提交，成功后跳转登录页 | P0 |
| R7 | 契约同步 | `api/openapi.yaml` 新增该接口 | P1 |

## 3. 方案对比与选型

### 3.1 会话吊销

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A 只清当前 Cookie | 改密后清 Cookie | 改动最小 | 其它浏览器/旧令牌仍有效 8h，泄露场景无改善 | 否 |
| B JWT 内嵌版本号 + Redis 计数 | `claims.ep`；改密 `INCR admin:epoch:<id>`；中间件比对 | 无迁移；一次 Redis GET；旧令牌立即失效；**读失败时 fail-open**（防缓存抖动全员掉线），Redis 重启后 epoch 归零 → 旧令牌全部 401 | Redis 无持久化，重启会迫使全部重新登录（安全方向） | ✅ 选用 |
| C DB 增加 `token_epoch` 列 | 每次请求查一次 DB | 持久化可靠 | 每个管理请求多一次 DB 往返；需要迁移 | 否 |

选型理由：管理端请求量极低但要「立刻失效」，Redis 已在用（登录限流），B 的成本最低。CLI `passwd` 也同步递增该计数，保证两条改密路径行为一致。

### 3.2 前端入口形态

顶栏现在是「用户名 + 登出按钮」。改为「用户名 + 修改密码 + 登出」两个按钮（不引入下拉菜单，改动面小、可测）：弹窗用 antd `Modal` + `Form`，字段为当前口令、新口令、确认新口令。

## 4. 总体架构

- `internal/admin/admin.go`
  - `claims` 增加 `Epoch int64`；`sign`/`parse` 带该字段。
  - `Service.tokenEpoch(ctx, adminID)`：`GET admin:epoch:<id>`，缺省 0；Redis 未配置（单测）时返回 0 并跳过校验。
  - `Auth` 中间件：解析成功后比对 `payload.Epoch == tokenEpoch`，不一致返回 `401 AUTH_INVALID_TOKEN`。
  - `ChangePassword(ctx, adminID, current, next)`：限流 → 查哈希 → 校验 → bcrypt 重算 → 事务更新 → `INCR epoch` → 清限流键。
  - `Routes`：在 `Auth` 组内新增 `r.Post("/admin/auth/password", s.handleChangePassword)`。
- `cmd/admin/main.go`：`passwd` 成功后同样 `INCR admin:epoch:<id>`（读取 `REDIS_URL`，缺失则跳过并提示）。
- `admin-web/src`
  - `api.ts` 增加 `changePassword(current, next)`。
  - `App.tsx` 顶栏增加按钮与弹窗；成功后 `api.logout()` → 跳 `/login`。
- `api/openapi.yaml`：新增路径与请求/响应 schema。

## 5. 数据模型

不新增表、不新增列。Redis 键：

| 键 | 类型 | 含义 | TTL |
| --- | --- | --- | --- |
| `admin:epoch:<admin_id>` | string(int) | 令牌版本，改密即 +1 | 无 |
| `rl:admin:passwd:<admin_id>` | string(int) | 改密失败计数 | 15 分钟 |

## 6. 接口设计

```http
POST /v1/admin/auth/password
Cookie: openquizgo_admin=…        # 或 Authorization: Bearer …
X-Admin-Request: 1                # Cookie 鉴权的写请求必须带
Content-Type: application/json

{"current_password":"…","new_password":"…"}
```

| 场景 | 状态码 | code | 说明 |
| --- | --- | --- | --- |
| 成功 | 200 | — | `{"status":"ok","re_login_required":true}`，同时下发失效 Cookie |
| 未登录/令牌失效 | 401 | `AUTH_INVALID_TOKEN` | 中间件返回 |
| 当前口令错误 | 401 | `AUTH_INVALID_CREDENTIALS` | 计入失败次数 |
| 新口令不合规 | 422 | `VALIDATION_ERROR` | 返回具体原因 |
| 尝试过多 | 429 | `RATE_LIMITED` | 15 分钟窗口 |
| 服务端错误 | 500 | `INTERNAL` | 记日志，不回显细节 |

## 7. 非功能要求

- 安全：bcrypt 默认 cost；错误信息不区分「用户不存在」；改密接口与登录接口限流独立，互不锁死。
- 性能：每管理请求 +1 次 Redis GET（亚毫秒）；无 DB 额外查询。
- 可观测：改密成功/失败写 `s.logger`（含 admin id，不含口令）。
- 兼容：旧令牌无 `epoch` 字段时视为 0，与缺省 Redis 值一致，升级不强制全员掉线。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Redis 重启后 epoch 归零 | 所有会话被踢，需重新登录 | 属安全失败方向；文档写明「Redis 重启后需重新登录」 |
| Redis 读超时/抖动 | 中间件读 `admin:epoch` 失败 | 失败时放行该请求（fail-open），只在版本确实不匹配时 401；避免缓存抖动把全部管理会话打成 401 |
| CLI 改密忘记递增 epoch | 旧令牌仍有效 | `cmd/admin passwd` 同步递增；单测覆盖 |
| 前端确认框与后端规则不一致 | 用户困惑 | 前端只做必填与两次一致校验，规则以后端为准并展示后端 message |
| 改密成功后仍未清 Cookie | 当前页后续请求 401 | 成功即 `logout` + 跳登录页 |
