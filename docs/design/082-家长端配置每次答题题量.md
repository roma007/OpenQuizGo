## 1. 背景与目标

### 现状与问题

单次答题的题量目前由 `rule.SessionSize` **自动推导**：按通过门槛与学科权重算出最少题数，再加 2 道，封顶 12 道。家长端没有任何地方能直接设置题量，家长只能通过改门槛间接影响题数，理解成本高。

用户要求：**家长端可以直接配置每次答题需要答多少道题目**。

### 本次目标（可验证）

- G1 家长端「电视设置」页新增「每次答题题量」，可选 **1–5 题**，新电视默认 **1 题**。
- G2 题量按**每台电视**独立生效（沿用 081 的 `tv_config`），同一家庭两台电视可设不同题量。
- G3 电视发起答题时，服务端严格按配置的题量组卷（`quiz_session.question_count` 等于配置值）。
- G4 存量电视升级后**不重置**当前实际题量：此前题量由 `SessionSize` 推导且最少 5 题，迁移统一回填 5（与升级前最接近）。
- G5 题量变小导致原通过门槛不可达时，服务端按该题量可达到的最高加权分**自动下调实际门槛**，避免孩子永远答不过。

### 非目标（明确不做什么）

- 不改孩子规则页（`watch_rule`）与旧激活码设备的题量推导逻辑，非电视设备仍按 `SessionSize` 自动推导。
- 不改判分、题库、难度、专题题包、每日一题、对战任何逻辑。
- 不新增电视端配置入口；电视端仍只有只读状态页。
- 不做「按学科分别配置题量」。

## 2. 需求与验收标准

| 编号 | 需求 | 验收标准 | 优先级 |
| --- | --- | --- | --- |
| R1 | 家长端可设题量 | 电视设置页有「每次答题题量」下拉，选项 1–5 题 | P0 |
| R2 | 按电视生效 | 两台电视分别设 1 题 / 5 题，各自组卷题量不同 | P0 |
| R3 | 精确题量 | 配置 N 题后创建会话，返回题目数 = N，`question_count` = N | P0 |
| R4 | 默认值 | 新登录电视 `question_count=1`；家长端显示 1 题 | P0 |
| R5 | 存量兼容 | 迁移把存量电视回填为 5 题（此前推导下限即 5 题），不统一重置为 1 | P0 |
| R6 | 门槛可达 | 题量不足导致门槛不可达时，实际通过门槛下调到该题量最高分 | P0 |
| R7 | 旧客户端兼容 | 旧版家长端未带 `question_count` 保存其他配置时，保留原题量而不是重置为 1 | P1 |
| R8 | 校验 | 题量超出 1–5 返回 422，不写库 | P0 |

## 3. 方案对比与选型

### 3.1 题量来源

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 继续由门槛推导（现状） | 无需改动 | 家长无法直接控制题量，概念绕 | 淘汰 |
| B `tv_config.question_count` 直接配置 | 语义直白、按电视独立、与 081 一致 | 需处理门槛可达性 | **选定** |

选型理由：用户要求「直接配题数」；081 已把电视配置统一收在 `tv_config`，新增一列即可，不动孩子规则。

### 3.2 与通过门槛的关系

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 题量固定、门槛原样保留 | 不改判分 | 1–2 题时门槛可能永远达不到，孩子被卡死 | 淘汰 |
| B 题量固定、门槛按题量下调到最高可达分 | 保证一定可过、无需新增概念 | 小概率降低实际难度 | **选定** |
| C 按题量重新计算门槛比例 | 难度曲线平滑 | 改动判分语义，家长更难理解 | 淘汰 |

选型理由：门槛只是「解锁所需分」，题量由家长显式选择后，保底可达比维持原门槛更重要。仅当 `pass_threshold > MaxScore(rule, n)` 时下调，正常 3–5 题不受影响。

## 4. 总体架构

| 模块 | 改动 |
| --- | --- |
| `migrations/00034_*.sql` | `tv_config` 新增 `question_count`，回填存量数据 |
| `internal/identity` | `TVConfig` 新增 `QuestionCount`；电视列表/详情查询带出 |
| `internal/rule` | 配置校验 1–5；`CanStartDevice` 返回题量；门槛按题量保底；`MaxScore` 导出 |
| `internal/quiz` | 组卷按 `question_count` 精确出题；快照携带题量 |
| `parent`（Flutter） | 电视设置页新增题量下拉，模型与序列化补字段 |
| `api/openapi.yaml` | `TVConfig` 契约补 `question_count` |

### 关键流程

```
家长端：电视设置 → 选「每次 3 题」→ 输入 PIN → PUT /v1/family/tvs/{id}/config
服务端：校验 1–5 → tv_config.question_count=3，version+1
电视：POST /v1/quiz/sessions
  → CanStartDevice 读取 tv_config → TVStartPlan{Rule, QuestionCount:3}
  → Rule.PassThreshold = min(原门槛, MaxScore(rule,3))
  → Select(..., QuestionCount:3) 精确选 3 题 → 落库 question_count=3
```

## 5. 数据模型

`tv_config` 新增：

| 字段 | 类型 | 约束 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `question_count` | integer | `between 1 and 5` | 1 | 每次答题题量 |

存量回填：此前题量由 `SessionSize` 推导，最少 5 题（`max(3, ceil(threshold/maxWeight)) + 2`，封顶 12），因此迁移把所有存量电视统一回填为 5，与升级前最接近；新电视走列默认值 1。

迁移只加列与约束，不删改既有字段；Down 删除约束与列。

## 6. 接口设计

| 类型 | 名称 | 入参 | 出参 | 说明 |
| --- | --- | --- | --- | --- |
| HTTP | `PUT /v1/family/tvs/{deviceID}/config` | `config.question_count`（1–5，可选） | `TVConfig` | 缺省（0）时保留原值，兼容旧客户端 |
| HTTP | `GET /v1/family/tvs`、`GET /v1/family/tvs/{id}` | — | `TVConfig.question_count` | 家长端读取 |
| HTTP | `POST /v1/quiz/sessions` | — | `questions[]`、`question_count` | 题量 = 配置值 |

错误码：`422 VALIDATION_ERROR`（题量不在 1–5）；`409 TV_CONFIG_CONFLICT`（乐观锁，沿用）。

## 7. 非功能要求

- 性能：仅多读一列，无额外查询；组卷池大小按题量计算，题量变小反而更快。
- 安全与权限：仍要求家长 PIN 与家庭归属校验；无新增公开入口。
- 可观测性：`quiz_session.question_count` 可核对实际下发题量；无需新增指标。
- 兼容性：旧家长端省略字段时保留原题量；旧电视端不感知该字段；非电视设备路径不变。

## 8. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| 小概率题量下门槛不可达 | 孩子永远答不过、无法解锁 | 高 | 服务端把实际门槛下调到该题量最高可达分 |
| 存量电视被重置为 1 题 | 家长感知「题变少了」 | 中 | 迁移按原推导结果回填（通常 4） |
| 旧家长端保存配置覆盖题量 | 题量被重置 | 中 | `question_count=0` 视为未提供，沿用库中原值 |
| 1 题时题库不足 | 发起答题失败 | 低 | 沿用 `INSUFFICIENT_POOL` 错误提示，家长可调大题量 |
| 1 题抽到趣味题 | 门槛很低 | 低 | 门槛按该题实际最高分计算，仍要求答对 |
