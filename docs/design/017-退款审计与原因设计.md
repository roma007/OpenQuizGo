## 1. 目标

退款需要留痕与可解释：

- 管理端退款必须填写原因（1–200 字）；
- 订单保存退款原因与操作人；
- 写入 `audit_log`，管理端审计页可检索到退款记录；
- 家长端订单可看到退款原因。

## 2. 数据模型

```sql
alter table membership_order add column refund_reason text not null default '';
alter table membership_order add column refunded_by uuid;
```

`refunded_by` 保存管理员账号 ID，不设外键，避免管理员删除后订单丢失。

## 3. 审计

退款成功后写入：

```json
{
  "actor_type": "admin",
  "actor_id": "<admin_id>",
  "action": "membership.order.refund",
  "target_type": "membership_order",
  "target_id": "<order_id>",
  "after_data": {
    "order_no": "M...",
    "amount_cents": 1990,
    "duration_days": 30,
    "reason": "用户申请退款"
  },
  "ip": "<client ip>"
}
```

审计写入失败不影响退款结果，但会记录服务端日志（本期直接忽略错误，与现有题库审计一致）。

## 4. 接口

`POST /v1/admin/membership/orders/{id}/refund`

```json
{"reason": "用户申请退款"}
```

- 原因必填，1–200 字；
- 已退款订单再次调用：返回原退款信息，不重复扣减（原因以首次为准）；
- 未支付订单：409。

## 5. 前端

- 管理端退款改为弹窗：显示订单信息 + 原因输入框，确认后提交；
- 订单表增加「退款原因」列；
- 家长端订单在退款后展示退款原因。

## 6. 风险

| 风险 | 对策 |
| --- | --- |
| 退款原因被绕过 | 服务端强制校验 |
| 审计与退款不一致 | 同一请求内先退款成功后写审计；失败仅记录日志 |
| 敏感信息写入审计 | 原因限制长度，管理端可见，家长端仅展示原因 |
