## 结论：电视端完全本地运行，不访问服务器

看代码能够确认，这个 TV 应用是一个**完全离线的单机守护端**，从它安装到设备上开始，就一直只读取本地数据：

| 位置 | 内容 |
| --- | --- |
| `tv/app/src/main/AndroidManifest.xml` | 只有 `FOREGROUND_SERVICE`、`RECEIVE_BOOT_COMPLETED` 两条权限，**没有 `INTERNET` 权限** |

也就是说，它连不上服务器；这里说的“连不上”指的是应用根本没有申请网络权限，所以即使有人想加请求，也会先运行失败。

## 具体存了什么

严格来说，TV 端**没有数据库**：没有 Room、SQLite 或 Realm，全部采用“文件加内存”的方式：

1. **题库**（`QuestionBank.kt`）— 打包在 APK 里的 `assets/questions.json`，共 **120 题**。启动时读进内存解析成 `List<LocalQuestion>`，并随机抽题，同时避免连续出现同一道题。运行时只读，不能改，也不能下载新题。
2. **运行状态**（`LocalSettings.kt`）— 用 DataStore Preferences，数据库文件名为 `local_guard`，只存三个键：
   - `quiz_enabled`（是否启用）
   - `elapsed_seconds`（已解锁时长）
   - `last_question_id`（上一题，用于去重）
3. **日志**（`LogStore.kt`）— 写入 `files/logs/guard.log`，单文件上限 1MB，滚转出一份 `guard.log.1`。只写入本地文件，不上传。

## ⚠️ 和设计文档的偏差，值得你知道

`docs/design/001` 描绘的是服务端主控架构：EdDSA 签名的离线租约、服务端判分、设备绑定、家长端实时下发规则。但 ROADMAP 里的 **077「TV 本地题库与定时答题（离线单机，v1.0.6）」** 走的是另一条路：TV 端先是做成了独立单机版。

这带来几个实际后果：

- 家长端**看不到** TV 上的答题情况，也**改不了** TV 的规则
- TV 端**没有**解锁额度的服务端扣减和审计
- 换设备或重装之后，状态全部丢失（本地 DataStore 跟着卸载清掉了）
- 服务端 `/v1/offline/lease` 等接口目前是“有接口、无客户端”的状态

# 077-TV 本地题库与定时答题设计

| 项目 | 内容 |

| 前置 | 家长端暂停推进；TV 0.4.4（依赖服务端激活） |

## 1. 背景与目标

### 1.1 现状与问题

- 家长端与服务器暂时不推进，TV 端现有流程依赖服务端：激活码绑定、创建答题会话、服务端判分、授权心跳、离线租约、家长远程解锁；
- 服务器和域名未准备，TV 安装后无法激活，整个守护流程不可用；
- 开发数据库中只有测试题（「导入题 1」「覆盖率测试」），没有可直接上线的真实题库；
- 现有 TV 端功能多（绑定、对战、诊断上传、会员），但当前阶段只需要「到时间弹一道题」。

### 1.2 本次目标（可验证）

1. TV 端完全离线可用：安装后不需要服务器、账号、家长端或网络。
2. 内置本地题库（≥100 道单选题），不按学龄/年级筛选，所有题目混合随机出题。
3. 首页只有一个业务开关：**定时答题**，默认开启。
4. 定时规则：累计视频播放满 **15 分钟** 自动弹出 1 道单选题；暂停播放、退出视频不计时。
5. 答对后继续观看；答错则保持答题界面，**直到答对**才可退出。
6. 关闭开关后不再弹出答题；重新开启后重新累计 15 分钟。
7. 重启电视/开机自启后开关状态保留，守护服务自动恢复。

### 1.3 非目标（明确不做什么）

- 家长端绑定、激活码、远程解锁、家庭 PIN；
- 服务端题库、答题会话、授权与心跳、离线租约、对战、会员；
- 学龄/年级/难度筛选、错题本、学习报告、数据上传；
- 在线更新题库（本期题库随 APK 打包，后续通过新版本替换）；
- iOS/Android 手机端。

## 2. 需求与验收标准

| 编号 | 需求 | 验收标准 | 优先级 |
| --- | --- | --- | --- |
| R1 | 离线可用 | 飞行模式、无网络、无服务器时，安装后即可进入首页并正常答题 | P0 |
| R2 | 本地题库 | APK 内置 `assets/questions.json`，≥100 道题，含题干、4 个选项、正确答案、解析 | P0 |
| R3 | 混合出题 | 出题不读取学龄/年级，所有题目等概率随机；连续两轮不重复同一题 | P0 |
| R4 | 15 分钟计时 | 仅媒体播放时累计，满 900 秒触发；暂停/退出不累计 | P0 |
| R5 | 开关 | 首页提供「定时答题」开关，默认开启；关闭后不触发 | P0 |
| R6 | 答对继续 | 答对显示正确反馈，点击「继续观看」退出答题并重新计时 | P0 |
| R7 | 答错锁定 | 答错停留原题，返回键无效，直到答对 | P0 |
| R8 | 自动弹出 | 到点后自动全屏弹出答题界面；被切走/关闭时守护服务自动重新拉起 | P0 |
| R9 | 开机自启 | 重启后服务恢复，开关与计时状态合理恢复 | P1 |
| R10 | 质量门禁 | 单元测试通过，Debug/Release 构建通过，真机/模拟器可验收 | P0 |

## 3. 方案对比与选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 保留服务端模式，增加离线缓存 | 改动小 | 仍需激活与服务器，违背本期目标 | 否决 |
| B. 新增「本地模式」分支，保留服务端代码 | 可随时切回 | 两套状态机并存，复杂且易误触网络 | 否决 |
| C. 删除服务端耦合，TV 改为纯本地单机应用 | 架构最简单，安装即用 | 需要重写状态机/答题界面并清理旧模块 | **采用** |
| D. 单独新建 TV 工程 | 隔离彻底 | 复制权限/无障碍/媒体检测等成熟代码，维护两份 | 否决 |

选型理由：当前阶段产品边界已经收敛为「本地题库 + 定时答题」，方案 C 可以显著降低运行复杂度和故障面；旧服务端代码保留在 Git 历史中，后续需要时再恢复。

## 为什么改（`docs/design/077` 第 1.1 节原话）

> - 家长端与服务器暂时不推进，TV 端现有流程依赖服务端：激活码绑定、创建答题会话、服务端判分、授权心跳、离线租约、家长远程解锁；
> - **服务器和域名未准备，TV 安装后无法激活，整个守护流程不可用**；
> - 开发数据库中只有测试题（「导入题 1」「覆盖率测试」），没有可直接上线的真实题库。

方案对比里明确**否决**了两条更保守的路：

| 方案 | 结论 |
| --- | --- |
| A. 保留服务端模式，加离线缓存 | 否决：仍需激活与服务器，违背本期目标 |
| B. 新增「本地模式」分支，保留服务端代码 | 否决：两套状态机并存，复杂且易误触网络 |
| **C. 删掉服务端耦合，改纯本地单机** | **采用** |

## 一个容易被忽略的关键点

077 的选型理由最后一句是：

> **旧服务端代码保留在 Git 历史中，后续需要时再恢复。**

也就是说，**这是有意的阶段性回退，并非架构上的最终决定**。整个服务端的租约、判分、设备绑定、家长端管控能力都还在（服务器上跑着、接口还在），只是 TV 端暂时不接了。

真要恢复，`git show eb2c728^:tv/app/src/main/java/com/openquizgo/guard/data/remote/GuardApi.kt` 就能把当时的实现全部取出来；但 077 之后 `StandardTable` 之类的界面和 `LocalGuardEngine` 已经重写过，直接 revert 会冲突，实际更省力的做法是**把 `GuardApi`、令牌、租约那几块作为新代码接回现有的 Local 引擎**（LocalGuardEngine 已经做过端口抽取，天然留了注入位）。这也正好是 075 那步「端口抽取与可注入时钟」留下的伏笔。
